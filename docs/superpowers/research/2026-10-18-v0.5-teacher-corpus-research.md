# v0.5 teacher LLM, runtimes, corpus and student fine-tuning: research brief

Date: 2026-10-18. Scope: the TELEClass-style learned element tagger. A local open-weight LLM labels a sample of elements, then a BERT-class student is fine-tuned on those labels.
Machine: Apple M1, 16 GB RAM, 8 GB budget per model process. TypeSafe Jev is excluded as teacher (Master Customer Agreement forbids distillation, see `2026-10-18-element-classification-research.md` section 0).

Conventions:
- **[unverified]** means I could not confirm the point from a primary source. Treat it as a lead.
- **[estimate]** means the number is my own arithmetic, not a published figure.
- Hugging Face (HF) facts come from `https://huggingface.co/api/models/<repo>` (sha, licence tag, parameter counts) or the model card, read on 2026-10-18. SHAs are the revision to pin.
- No weights were downloaded and no code was executed. Code in section 2.4 is written from verified API signatures and is **untested**.
- HF `usedStorage` is not a reliable file size for several repos (see 1.3). Memory figures below are my arithmetic unless a source is cited.

## 0. Top-line recommendations

1. **Teacher: `mlx-community/Qwen3-4B-Instruct-2507-4bit`** at revision `50d427756c6b1b2fe0c0a10f67fbda1fc8e82c1b`.
   - Apache-2.0, no output-use clause, 4.02B params, about 2.3 GB at 4-bit, non-thinking only.
   - Source: [base card](https://huggingface.co/Qwen/Qwen3-4B-Instruct-2507), [MLX repo API](https://huggingface.co/api/models/mlx-community/Qwen3-4B-Instruct-2507-4bit).
2. **Fallback: `mlx-community/Qwen3-8B-4bit`** at revision `545dc4251c05440727734bcd94334791f6ab0192`.
   - Apache-2.0, about 4.6 GB, fits the 8 GB budget with short contexts.
   - Same tokenizer and prompt format, so it is a drop-in accuracy escalation for low-confidence elements.
   - Caveat: there is no "2507 Instruct" 8B; the 8B is the hybrid thinking model (set `enable_thinking=False`).
   - If a second, licence-diverse family is wanted instead: `mlx-community/Phi-4-mini-instruct-4bit` (MIT, about 2.2 GB).
3. **Do not use as teacher:** Llama 3.2 3B (output-trained models must start with "Llama" in their name) and Gemma 3 4B (a model trained on Gemma outputs is a "Model Derivative" under the Gemma terms). Details in 1.1.
4. **Runtime: mlx-lm** (MIT, 0.32.2). Score K labels with one forward pass per element, reading the next-token log-probs at the answer position. Cache the shared taxonomy prefix and trim the cache back after each element. This makes the cost roughly the element's own tokens, not the whole prompt. Pattern in 2.4.
5. **Corpus.** Start with EDGAR Form ARS PDFs (roughly 2,158 ARS hits in Mar-Apr 2025 alone), then govinfo GAOREPORTS (16,569 packages modified since 2025-01-01), Federal Reserve PDFs, RFC PDFs (newer RFCs only), arXiv CC-BY/CC0 via OAI-PMH `arXiv` format, and govinfo USCOURTS in place of CourtListener (CourtListener's documented limit is 5/min).
6. **Student: fine-tune with plain `transformers` (`Trainer` or own loop), not sentence-transformers.** Pad to a multiple of 64 to stop the MPS graph cache growing. Plan for 1-3 h per epoch for 20-50k short texts **[estimate]**. Do a frozen-embedding head first.

- The Qwen3-4B-Instruct-2507 MLX card lists 2.26 GB for the artifact ([page](https://huggingface.co/mlx-community/Qwen3-4B-Instruct-2507-4bit)).

## 2. Runtimes

### 2.1 mlx-lm

- **Licence:** MIT, Copyright Apple Inc. ([LICENSE](https://raw.githubusercontent.com/ml-explore/mlx-lm/main/LICENSE), [PyPI](https://pypi.org/pypi/mlx-lm/json)).
- **Version:** 0.32.2 on PyPI. `requires_python >=3.11`; requires `mlx>=0.32.2` on Darwin and **`transformers>=5.7.0`**. The repo already pins `transformers>=5` and `sentence-transformers>=6` ([pyproject.toml](../../../pyproject.toml)), so this is compatible if the resolver picks 5.7 or later. Do not run a plain `uv sync` (machine constraint); install into a separate environment so the torch-free core is untouched.
- **Install:** `pip install mlx-lm` or `conda install -c conda-forge mlx-lm` ([README](https://raw.githubusercontent.com/ml-explore/mlx-lm/main/README.md)).
- **API surface used here** ([generate.py](https://raw.githubusercontent.com/ml-explore/mlx-lm/main/mlx_lm/generate.py), [cache.py](https://raw.githubusercontent.com/ml-explore/mlx-lm/main/mlx_lm/models/cache.py), [qwen3.py](https://raw.githubusercontent.com/ml-explore/mlx-lm/main/mlx_lm/models/qwen3.py)):
  - `load(path_or_hf_repo, ..., revision=None)` returns `(model, tokenizer)`.
  - `model(inputs, cache=None)` returns logits, expected shape `(batch, seq, vocab)` (inferred from the layer definitions).
  - `make_prompt_cache(model)`, `trim_prompt_cache(cache, num_tokens)`, `can_trim_prompt_cache(cache)`, `save_prompt_cache(...)`.
  - `stream_generate(...)` yields `GenerationResponse` with a `logprobs: mx.array` vector per token (log-probs over the whole vocabulary). `generate()` returns only text.
  - `generate_step(..., prompt_cache=None, logits_processors=None, prefill_step_size=2048)`.
  - `batch_generate(prompts: List[List[int]], return_logprobs: bool = False)` exists but returns logprobs of the *sampled* tokens only. It is not what constrained scoring needs.
- **Memory knobs:** `mx.set_memory_limit`, `mx.set_cache_limit`, `mx.clear_cache`, `mx.get_peak_memory` ([docs](https://ml-explore.github.io/mlx/build/html/python/memory_management.html)). The README mentions `sudo sysctl iogpu.wired_limit_mb=N` only for models large relative to RAM.
- **Server:** `mlx_lm.server` returns `logprobs` for chat completions (1-10 top tokens). "A quantized KV cache does not support batching" and the server "is not recommended for production" ([SERVER.md](https://raw.githubusercontent.com/ml-explore/mlx-lm/main/mlx_lm/SERVER.md)). It only returns top-k tokens, so it cannot score an arbitrary label set. Use the Python API.

**Speed on M1 (no primary measurement found for mlx-lm + a 4B model).**
- I did not find a published mlx-lm number for M1 + Qwen3-4B. Run `mlx_lm.benchmark` or time a fixed prompt on the target machine before committing.
- Closest primary datapoint: llama.cpp, Llama-7B Q4_0, M1 with 8 GPU cores: prompt processing (PP) 512 = 117.96 t/s, text generation 128 = 14.15 t/s ([llama.cpp discussion 4167](https://github.com/ggml-org/llama.cpp/discussions/4167)). The same table has the 7-core M1 at 107.81 and 14.19.
- Scaling by parameters (7B to 4B) gives roughly **150-250 prefill tokens/s** for a 4B 4-bit model **[estimate]**. Decode is memory-bandwidth-bound; scoring does not decode.
- A secondary source (search snippet, page returned 403 so I did not read it) quotes MLX at about 438 t/s prompt processing on an older M1-era run for a 7B 4-bit model **[unverified]** ([Medium](https://medium.com/@andreask_75652/benchmarking-apples-mlx-vs-llama-cpp-bbbebdc18416)).
- Prefill is compute-bound on M1, so batching several elements into one forward pass will help little **[estimate]**. Batching helps decode, which this task does not use.
- **Budget:** with the taxonomy prefix cached, about 150-250 new tokens per element means about 1 s per element, so 2,000 elements is about 35 min and 20,000 about 3-4 h **[estimate]**. Without prefix caching a 1,500-token prompt costs about 7 s per element **[estimate]**. Caching is mandatory.
- **bf16 on M1:** the MLX 4-bit repos keep scales and norms in bf16. Secondary sources say M1/M2 have no native bf16, so bf16 matmuls can be slow and fp16 faster (one model card claims about 60% lower prefill time on an M1 Pro) **[unverified, not MLX-official]** ([model card](https://huggingface.co/xunker/CodeLens-7B-MLX), [Eclectic Light on ARMv8.5](https://eclecticlight.co/2024/01/13/how-m1-macs-may-lag-behind/)). Test `model.set_dtype(mx.float16)` once; check that the Qwen3 logits do not overflow.

### 2.2 transformers on MPS (fallback)

From the official Apple Silicon page ([HF docs](https://huggingface.co/docs/transformers/perf_train_special)):
- `device_map="mps"` loads safetensors straight onto MPS. SDPA is the default and recommended attention for training.
- Quantisation on MPS: "Metal" quantises to 2/4/8 bits at load; bitsandbytes does 4-bit with native MPS kernels. Both are described for inference or LoRA, so they are a way to hold a 4B or 8B teacher in 4-bit without MLX. **[unverified in practice: I did not test speed or logprob exactness.]**
- Without quantisation, fp16 weights are 2 bytes per param: Qwen3-1.7B is about 3.4 GB, Qwen3-4B about 8 GB (over budget) **[estimate]**. So the unquantised fallback only works for the 1.7B.
- `PYTORCH_ENABLE_MPS_FALLBACK=1` sends unsupported ops to CPU. `PYTORCH_MPS_HIGH_WATERMARK_RATIO` (default 1.7) is a hard cap on allocations, where 1.0 matches the device's recommended maximum ([PyTorch MPS env vars](https://docs.pytorch.org/docs/2.14/mps_environment_variables.html)).
- Scoring pattern is identical to 2.4: one forward pass, `log_softmax` of the last position, gather candidate token ids. `model(**inputs).logits[:, -1]` in `torch.no_grad()`.

All server routes return only the top-k tokens per position. That is enough when each label is a single letter that appears in the top 20, but it cannot score an arbitrary multi-token label, and a letter outside the top-k is simply missing. The in-process mlx-lm path in 2.4 gets exact log-probs for any token. Prefer it.

### 2.4 Code pattern: score K candidate labels with mlx-lm

**Untested.** Written from the verified signatures above. First run it on Qwen3-1.7B-4bit as a smoke test, and check that the letter-token assertion holds for the pinned tokenizer.

Design:
- Put the taxonomy and instructions in a fixed **prefix**. Prefill it once and keep the KV cache.
- Per element: run only the element text and the answer cue, read the next-token distribution, then `trim_prompt_cache` back to the prefix length.
- The prefix must end on a tokenisation boundary (a newline or special token) so that `ids(prefix) + ids(suffix)` equals `ids(prefix + suffix)`. Assert this on a few examples.

```python
import mlx.core as mx
from mlx_lm import load
from mlx_lm.models.cache import make_prompt_cache, trim_prompt_cache, can_trim_prompt_cache

REPO = "mlx-community/Qwen3-4B-Instruct-2507-4bit"
REV = "50d427756c6b1b2fe0c0a10f67fbda1fc8e82c1b"
mx.set_memory_limit(6 * 1024**3)            # leave headroom under the 8 GB budget

model, tok = load(REPO, revision=REV)

TAGS = ["paragraph", "heading", "list_item", "table", "caption", "footnote", "other"]   # example taxonomy
LETTERS = "ABCDEFGHIJKLMNOPQRSTUVWXYZ"[: len(TAGS)]

system = "Classify the document element. Answer with one letter.\n" + "\n".join(
    f"{l}. {t}" for l, t in zip(LETTERS, TAGS))

# Split the chat-templated prompt at the element slot.
SENTINEL = "␞ELEMENT␞"
full = tok.apply_chat_template(
    [{"role": "system", "content": system},
     {"role": "user", "content": SENTINEL}],
    add_generation_prompt=True, tokenize=False)
prefix_txt, suffix_tmpl = full.split(SENTINEL)   # prefix ends right after the user turn opens

prefix_ids = tok.encode(prefix_txt, add_special_tokens=False)
cache = make_prompt_cache(model)
model(mx.array(prefix_ids)[None], cache=cache)           # prefill once
mx.eval([c.state for c in cache])
assert can_trim_prompt_cache(cache)

# One token id per letter; check it is a single token for this tokenizer.
letter_ids = []
for l in LETTERS:
    ids = tok.encode(l, add_special_tokens=False)
    assert len(ids) == 1, (l, ids)
    letter_ids.append(ids[0])
letter_ids = mx.array(letter_ids)

def score_letters(text: str):
    """Return (probs over K tags renormalised, mass on the K letters)."""
    ids = tok.encode(text + suffix_tmpl, add_special_tokens=False)
    logits = model(mx.array(ids)[None], cache=cache)[0, -1].astype(mx.float32)
    lp = logits - mx.logsumexp(logits)                   # full-vocab log-softmax
    cand = lp[letter_ids]                                # K log-probs
    out = (cand - mx.logsumexp(cand)), mx.exp(mx.logsumexp(cand))
    mx.eval(out)
    trim_prompt_cache(cache, len(ids))                   # back to the prefix
    return out   # out[1] near 1.0 = the model answered with a letter; low = abstain / bad prompt

def score_names(text: str, names: list[str]):
    """Sum of token log-probs of each full label string (multi-token labels)."""
    base = tok.encode(text + suffix_tmpl, add_special_tokens=False)
    scores = []
    for name in names:
        cont = tok.encode(name, add_special_tokens=False)
        ids = base + cont
        logits = model(mx.array(ids)[None], cache=cache)[0].astype(mx.float32)
        lp = logits - mx.logsumexp(logits, axis=-1, keepdims=True)
        # row i predicts token i+1; the first label token is predicted at row len(base)-1
        rows = mx.arange(len(base) - 1, len(ids) - 1)
        s = mx.take_along_axis(lp[rows], mx.array(cont)[:, None], axis=1).sum()
        mx.eval(s); scores.append(s.item())
        trim_prompt_cache(cache, len(ids))
    return scores     # sum of logprobs; do NOT length-normalise unless you calibrate for it
```

Notes:
- Letter scoring is one forward pass per element, with K labels read for free. Prefer it. Use the name scorer only when labels cannot be mapped to unique single tokens, since it costs K forward passes.
- `score_letters` keeps the full-vocab log-softmax so the "mass on letters" is meaningful. Use that mass, and the entropy of the K-way distribution, as the teacher's confidence for TELEClass-style filtering or for routing to the Qwen3-8B fallback.
- Randomise the letter order per run (or run two orders and average) to reduce position bias in multiple-choice scoring **[general practice, not verified here]**.
- With `tie_word_embeddings` and a 151,936-token vocabulary, `model(...)` returns logits for every suffix position (about 0.3 MB per position in bf16). Keep suffixes short or evaluate the last position only, so logits do not dominate memory.
- Call `mx.clear_cache()` every few hundred elements and log `mx.get_peak_memory()`.
- Save the prefix cache with `save_prompt_cache` if the prefix will be reused across processes.

## 4. Student fine-tuning on M1 / 8 GB

### 4.1 Measurements found

There is **no published measurement for a ~150M encoder at seq 256-512 with gradient checkpointing on a base M1.** What exists:

- [lucadiliello/pytorch-apple-silicon-benchmarks](https://github.com/lucadiliello/pytorch-apple-silicon-benchmarks): bert-base-cased sequence classification, **fp32**, time for **100 steps**, no gradient accumulation, PyTorch `1.13.0.dev20220601` (old). On **M1 Max, 32-core GPU, 32 GB**:

| Batch | Seq len | M1 Max GPU | M1 Max CPU |
|---|---|---|---|
| 16 | 128 | 1m 3s | 2m 29s |
| 64 | 128 | 2m 57s | 8m 32s |
| 256 | 128 | 1h 49m 9s | 50m 10s |
| 16 | 512 | 9m 28s | 11m 22s |
| 64 | 512 | 3h 26m 4s | 1h 21m 2s |
| 256 | 512 | out of memory | 6h 33m 7s |

  The author notes large batches kept running by spilling to swap, which "really slows down training".
- [pytorch/pytorch #82707](https://github.com/pytorch/pytorch/issues/82707): BERT fine-tuning on MRPC, 3 epochs, M1 with 14 GPU cores and 16 GB. PyTorch 1.12.0: MPS 772 s versus CPU 1002 s, but final accuracy 0.70 versus 0.85. A nightly from Aug 2022 gave MPS 608 s versus CPU 982 s with accuracy within about 0.6%. Closed as fixed 2022-08-08; a July 2024 comment still saw MPS about 0.02 lower than CPU. **Compare MPS against a CPU run on a small subset to check for a regression.**

**Derived estimate (mine).**
- From the table: M1 Max, bs16, seq 128 is about 3.2k tokens/s; bs16, seq 512 is about 1.4k tokens/s (fp32, 2022 PyTorch).
- A base M1 has 8 GPU cores versus 32, so assume about a quarter of that, about 0.8k tokens/s at seq 128 and about 0.35k at seq 512 for BERT-base.
- UltraBERT-150M has about 1.5x the compute of BERT-base **[estimate; 24 layers, h768, per the earlier brief]**, so roughly 0.5k tokens/s at seq 128 and 0.25k at seq 512.
- 30k texts x 128 average tokens = 3.8M tokens per epoch, so **about 2 h/epoch**. Add about 30% for gradient checkpointing, so about 2.5 h/epoch. 50k texts at 256 average tokens (12.8M tokens) is about 7 h/epoch.
- Newer PyTorch and fp16/bf16 autocast should be faster; 2x is plausible **[unverified]**.
- **Plan on 1-3 h/epoch for 20-50k texts under about 128 tokens, and 4-8 h/epoch at 256-512 [estimate]**, 2-3 epochs. Measure 200 steps on the real machine first, as the earlier brief also advises.

**Memory.** The earlier brief's arithmetic for a 150M model at seq 512 stands: about 2.4 GB for fp32 weights, gradients and Adam moments, plus roughly 0.5 GB per sample per layer-stack in bf16/fp16 without checkpointing ([earlier brief section 7](2026-10-18-element-classification-research.md)). Batch 4-6 without checkpointing, or batch 16+ with it, fits 8 GB **[estimate]**. At seq 256 the activations halve or better.

### 4.2 Known MPS issues and mitigations

- **MPS graph cache growth.** "MPS compiles a Metal kernel for each tensor shape it sees and keeps them in a graph cache that is never evicted. Training with variable-length inputs adds a kernel for every new shape and can run out of unified memory." Fix: `DataCollatorWithPadding(tokenizer, pad_to_multiple_of=64)` ([HF Apple Silicon page](https://huggingface.co/docs/transformers/perf_train_special)). Use length-bucketed batches with a handful of fixed shapes.
- **Mixed precision.** The HF page says both `bf16` and `fp16` work in `Trainer` on MPS. M1 lacks native bf16 hardware **[unverified for MPS specifically; see 2.1]**, so benchmark `fp16` autocast against `bf16` and keep the loss scaler on for fp16.
- **Attention.** Use SDPA for training. The Metal flash-SDPA kernel does not compute gradients for the Q, K, V projections, so do not select it ([same page](https://huggingface.co/docs/transformers/perf_train_special)).
- **Unsupported ops.** `PYTORCH_ENABLE_MPS_FALLBACK=1` runs them on CPU. Cap allocations with `PYTORCH_MPS_HIGH_WATERMARK_RATIO`. A ratio of 0.0 disables the cap, so do not set it to 0 ([PyTorch env vars](https://docs.pytorch.org/docs/2.14/mps_environment_variables.html)). The relationship between this ratio and the "8 GB per model process" budget is **[unverified]**: the ratio is relative to the device's recommended working set, not to a number of bytes.
- **Gradient checkpointing on MPS.** I found no MPS-specific bug report. **[unverified]**
- **sentence-transformers on MPS** (the stack the repo already uses for embeddings):
  - Past breakage: `CachedMultipleNegativesRankingLoss + MPS is broken` ([issue 3564](https://github.com/huggingface/sentence-transformers/issues/3564), fixed by [PR 3812](https://github.com/huggingface/sentence-transformers/pull/3812) merged 2026-06); [PR 3818](https://github.com/huggingface/sentence-transformers/pull/3818) removed CUDA-only AMP and sparsity code so MPS works.
  - v5.7.0 (2026-08-06) fixed a bug in the cross-encoder `CachedMultipleNegativesRankingLoss`: the backward pass used different dropout masks than the forward pass on CUDA and MPS, "silently biasing gradients"; fixed by [PR 3862](https://github.com/huggingface/sentence-transformers/pull/3862) ([release](https://github.com/huggingface/sentence-transformers/releases/tag/v5.7.0)). Any model trained on MPS with a sentence-transformers version before 5.7 and a cached loss is suspect.
  - A memory-growth report on Apple Silicon for `SparseEncoder.encode_document` ([issue 3851](https://github.com/huggingface/sentence-transformers/issues/3851)) was closed and the author said it is not a confirmed leak.
  - These issue summaries came from a GitHub search result summarised by my fetch tool, not from reading each thread. Re-read the issues before relying on them.
  - A forum report (M2, non-sentence-transformers) describes unbounded memory growth until OOM and says `torch.mps.empty_cache()` did not help ([HF forum](https://discuss.huggingface.co/t/running-out-of-memory-in-the-summary-example/175777)). That is a single anecdote.
- **Recommendation.** The student is a classifier, not an embedder. Train it with `AutoModelForSequenceClassification` and `Trainer`, which the HF page documents for MPS. This avoids the sentence-transformers loss and cache paths above. UltraBERT carries a `custom_code` tag in HF (checked on the Embed-150M card, [API](https://huggingface.co/api/models/dmis-lab/UltraBERT-Embed-150M)), so it needs `trust_remote_code=True`. Pin the revision and read that code before running it.
- **Cheaper first stage** (from the earlier brief): train a logistic-regression or MLP head on the UltraBERT-Embed vectors docrooter already computes. Full fine-tuning only if that plateaus.
