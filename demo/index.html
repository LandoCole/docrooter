Haiku's tokens are exact, from the API's usage. UltraBERT, a local embedding model, makes no LLM call, so its tokens estimate what the same views would cost an LLM. Haiku ran with thinking off and batched calls: one call for the type, a few for the sections, each option listed once.

A note on the numbers. The 113 gold documents span 8 types (annual reports, fact sheets, prospectuses, government reports, contracts, court opinions, research papers, standards), and the doc-type rules were revised once after looking at them, so treat the gold column as development numbers. The held-out set is the clean measure. The section labels were written by Claude annotators for evaluation only.

How it works

A context ladder. doc-rooter reads a PDF or Markdown file into a section tree, then renders it at four rungs, each adding one field: the headings (title, page and section counts, the contents), then key terms, then the opening sentences, then the whole text, budgeted to a 16,000-token prompt. You choose the rung; the benchmark measures what each one buys.

Two flows. Doc first names the type from the document view, then tags the sections with that type's own labels. Sections first tags the level-1 and level-2 sections against a shared catalogue of 112 section types, and lets rules (a balance sheet means a financial report, an opinion and a holding mean a court opinion) narrow or decide the type, asking the model only when they can't.

Every token counted. Calls are batched, so each option list is sent once per stage, not once per section. Every call reports its exact prompt and completion tokens, and every section tag carries its share.

Why

Sending a hosted LLM the whole document is the easy default, and it's expensive at volume: a 200-page filing is 100,000 tokens before the model reads a word of the question. I built doc-rooter to find the least a model needs to see. The answer surprised me. For the document's type, the title and the contents were as good as anything richer, and better than the full text, at about an eighth of the tokens. More context gave the model more to be distracted by.

doc-rooter is the next step after my document classifier, which names a financial document's type from a short overview in one question to Jev. doc-rooter takes the same idea further as a standalone package: it reads a PDF into its section tree, tags the sections as well as the document, lets the sections decide the type, works with any model you plug in, and measures what each extra piece of context buys.
